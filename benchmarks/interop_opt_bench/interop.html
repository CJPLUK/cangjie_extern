Overhead of interop operations

Batching

A Cangjie thread calls an ArkTS function that computes 2x + 1, 2,000 times. Each call is posted to the ArkTS thread and followed by w µs of Cangjie work.
Naive: one posted task per call, wait for it immediately.
Batching: one posted task for b consecutive calls, wait for it immediately, then do the b works.

// E1, E2, E3: independent extern expressions, of type Float64
// Cangjie work using the results
func work(a: Float64, b: Float64, c: Float64): Unit
func post<T>(task: () -> T): Future<T>  // runs task on the ArkTS thread
naive
let a = «post({ => E1 }).wait()»
let b = «post({ => E2 }).wait()»
let c = «post({ => E3 }).wait()»
work(a, b, c)
optimised
let (a, b, c) =
    ‹post({ => (E1, E2, E3) })›
        ‹.wait()›
work(a, b, c)
source, with Extern
let a: Extern<ArkTS> = E1
let b: Extern<ArkTS> = E2
let c: Extern<ArkTS> = E3
work(a, b, c)
Benchmarked code
// actual benchmarked code: n calls, each followed by w µs of Cangjie work
// f: the ArkTS function (x) => 2 * x + 1
naive
for (i in 0..n) {
    acc += post({ => f(i) }).wait()
    work()                                  // w µs
}
optimised (batching: b calls per posted task)
for (i in 0..n : b) {
    acc += post({ => f(i) + … + f(i + b - 1) }).wait()
    for (j in 0..b) { work() }              // b × w µs
}

Futures

Same program as the batching slide: 2,000 calls of the ArkTS function computing 2x + 1, each posted to the ArkTS thread and followed by w µs of Cangjie work.
Naive: wait for each result immediately.
Futures: keep d calls in flight, i.e. post d more calls before waiting for a result.

// E1, E2: independent extern expressions, of type Float64
func work1(): Unit                      // Cangjie work, independent of E1, E2
func work2(): Unit
func use(a: Float64, b: Float64): Unit  // Cangjie work using the results
func post<T>(task: () -> T): Future<T>  // runs task on the ArkTS thread
naive
let a = «post({ => E1 }).wait()»
work1()
let b = «post({ => E2 }).wait()»
work2()
use(a, b)
optimised
let fa = ‹post({ => E1 })›
work1()
let fb = ‹post({ => E2 })›
work2()
use(‹fa.wait()›, ‹fb.wait()›)
source, with Extern
let a: Extern<ArkTS> = E1
work1()
let b: Extern<ArkTS> = E2
work2()
use(a, b)
Note: this optimisation applies only when E1 and E2 are known not to cause data races by calling back into Cangjie, which primarily means they contain no call to an ArkTS function.
Benchmarked code
// actual benchmarked code: n calls, each followed by w µs of Cangjie work
// f: the ArkTS function (x) => 2 * x + 1
naive
for (i in 0..n) {
    acc += post({ => f(i) }).wait()
    work()                                  // w µs
}
optimised (futures: d calls in flight)
for (i in 0..n) {
    fut[i] = post({ => f(i) })
    if (i >= d) { acc += fut[i - d].wait() }
    work()                                  // w µs
}

Coalesced property access

Cangjie code on the ArkTS thread reads the path o.k0.k1… of depth d.
Naive: one getProperty per level, d FFI calls.
Coalesced: one FFI call for the whole path.

let o: JSValue            // root object
var v: JSValue            // value along the path
let readPath: JSFunction  // generated ArkTS function (o) => o.k0.k1 … k7
naive
v = o.«getProperty("k0")»
v = v.«getProperty("k1")»
...
v = v.«getProperty("k7")»
optimised
v = ‹readPath.call(o)›
let o: Extern<ArkTS>  // root object
source, with Extern
let v: Extern<ArkTS> = o.k0.k1.k2.k3.k4.k5.k6.k7
Disclaimer
The library has no operation that reads several properties in one FFI call. The coalesced variant calls an ArkTS function that reads the path, (o) => o.k0.k1 … k7: one FFI call. A native multi-read would not enter a function and would be at least as fast.

Scoped temporaries

There are two kinds of references to ArkTS objects: volatile, cheap references, valid only until the current scope ends, and persistent, expensive ones (a GC root in the engine plus a Cangjie object with a finalizer). Letting a volatile reference escape its scope is unsafe, so asObject(), asArray(), asString() and rt.string() always create a persistent reference. Often this persistence is unnecessary: the value is a temporary that never leaves the scope.
Naive: temporaries bound as persistent references.
Scoped: the same temporaries bound as volatile references; the compiler must ensure they do not escape.
Each of N steps reads x[i].inner.v and calls f(s) = s + "!"; times are per step.

let arr: JSArray   // ArkTS array of objects {inner: {v: number}}
let s: String      // a Cangjie string
let f: JSFunction  // the ArkTS function (s) => s + "!"
var sum: Float64   // running sum
naive
let b: «JSObject» = arr[i]«.asObject()»
let c: «JSObject» =
    b["inner"]«.asObject()»
sum += c["v"].toNumber()

let t: «JSString» = «rt.string(s)»
let r: «JSString» =
    f.call(t.toJSValue())«.asString()»
optimised
let b: ‹JSValue› = arr[i]
let c: ‹JSValue› =
    b.getProperty("inner")
sum += c.getProperty("v")
        .toNumber()

let r: ‹JSValue› =
    f.call(‹s.toJSValue(rt)›)

String caching

Cangjie exports 10,000 records with string fields to an ArkTS array.
Naive: names and values converted on every use.
Names cached: names created once.
Names + values cached: string values also reused, through a String → JSString cache.

let o: JSObject                   // ArkTS object being filled
let list: JSObject                // ArkTS array receiving the objects
let s: String                     // a field value, as a Cangjie string
func cached(s: String): JSString  // String -> JSString, created on first use
naive
o.setProperty(«"name"»,
    «rt.string(s)».toJSValue())
list.callMethod(«"push"»,
    [o.toJSValue()])
optimised
o.setProperty(‹cached("name")›,
    ‹cached(s)›.toJSValue())
list.callMethod(‹cached("push")›,
    [o.toJSValue()])
let o: Extern<ArkTS>     // ArkTS object being filled
let list: Extern<ArkTS>  // ArkTS array receiving the objects
let s: String            // a field value, as a Cangjie string
source, with Extern
o.name = s
list.push(o)

Combined optimisations: search-as-you-type

ArkTS holds 1,000 items, each with a title and a 200-character description. Cangjie threads score each item against a query (approximate substring edit distance) and push a result object back.
Futures: reads issued 8 items ahead, writes waited for at the end.
Batching: 8 items per posted task.
Coalesce, scoped, cache: applied together, inside each task.
Pure ArkTS: the same search in ArkTS, single-threaded.

Live graph layout

ArkTS renders N nodes in the UI. Every frame, Cangjie code reads the position and mass of every node, computes the forces between them, and writes the new positions.
Naive: without optimisations.
Optimised: with the optimisations on.
Pure ArkTS: the same computation written in ArkTS.

Frame time: one simulation step, from reading the nodes to writing them back.
